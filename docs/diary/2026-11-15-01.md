# Diary — 2026-11-15 (01)

## A connection that serves (roadmap 0011)

ask is building `ask serve` on `JSONRPCConnection` (the Agent Client Protocol: JSON-RPC, a message a line, the agent in the
server's role). Its spike answered `initialize` and showed two things the client's role had never needed:

| Claim | Probe | Verdict |
|---|---|---|
| Requests are handled in the order they arrive | `session/new`, `initialize`, `session/teleport` in one write to a server that refuses everything before `initialize` | **Fails**: the third was refused as "before initialize"; each request's handler runs in a task of its own |
| A line that is not a message is answered | `this is not json` and a `"jsonrpc":"1.0"` request, to the same server | **Fails**: no answer to either |
| The new tests can fail | admission moved into the child task and the refusals reversed; then the work awaited on the reader | **Holds**: five tests red; then the waiting test at its time limit |

The first matters where a protocol's messages depend on one another: a cancellation sent right after the request it cancels is a
notification, delivered in order on the reader, and could be handled before that request's task had started.

`init(serving:…admit:…)` splits a request in two: `admit`, on the reader and in order, returns the work, which runs in a child
task. The old initializer is untouched. A serving connection answers what it cannot read; a client's still says nothing.

51 tests in `AemiJSONRPCTests` (44 and these 7) and the whole package (466, 51 and 2) pass with `AD_TYPECHECK_BUDGET_MS=250` (at the default 100 ms
`emitsEventsInDocumentOrder` took 102 ms to type-check on this machine, before this change too: roadmap 0010 saw the same).
